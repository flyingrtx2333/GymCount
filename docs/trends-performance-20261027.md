# 趋势筛选卡顿修复 · 2026-10-27

## 原因与改动

`RecordTrendsView.points` 原为计算属性，每次读取都会调用 `RecordTrendPoint.summarize`，遍历整批记录、分桶及汇总时长。图表各 mark 内的 scale／unit／barWidth／selected 又间接读取它；数据、指标及汇总方式切换时，Swift Charts 多次构建内容，将本应一次完成的汇总扩大成数千次主线程工作。原生 CPU 采样能在 `RecordTrendsView.chart` 内容构建路径中看到重复的 `RecordTrendPoint.summarize`。

- 仅在记录、动作／日期筛选、指标或汇总方式变化时生成并保留 points 和 resolved grouping。
- 图表逐 mark 构建前，一次取出选中 ID、比例、单位、柱宽、坐标日期及可见范围；横滑和点选不重新遍历历史做汇总。
- 保留已有统计口径、缺失值、选中清理、偏好保存和同步更新路径；没有更改 Watch、计数算法、数据格式或视觉规范。

## 原生工作量对比

固定复用既有大屏 iPhone，使用同一份 82 条真实历史（323 次），在隔离安装／存储内执行同样的动作、四种指标、三个时间段及日／周／月汇总切换。没有生成训练和传感器数据。

| 同一流程的统计工作 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 完整汇总调用 | 52,210 次 | 17 次 |
| 汇总函数累计耗时 | 4,623.37 ms | 2.00 ms |

比较采用 `BeforeFinal.xcresult` 和 `After.xcresult` 的通过运行，临时计数和计时探针仅放在隔离副本，同一探针对两边生效；比较运行没有同时启动 CPU 采样器。探针及额外 CPU 采样均不进入产品源码，最终另执行纯应用副本验证。

这些数字是整套操作的汇总工作量，不能当作一次点击延迟或真机帧率。CADisplayLink 的最大间隔包含菜单／自动化影响，不作为帧率结论。额外 CPU 栈显示修复后重复汇总已不再是热点，较长的自动化采样路径有 `XCTElementSnapshotRequest`／`AXUIElementCopyParameterizedAttributeValue` 读取辅助功能树的开销，不将其全部归因为日常操作卡顿。

初轮原生脚本的“全部时间”查询同时匹配菜单项和筛选控件，导致脚本失败；已限定菜单项，随后相同工作量的基线和修复版均通过，初轮结果保留。
